# Linux Kernel Pull Request Generator (`kdev-pull-request`)

## Overview

This skill prepares a Linux kernel Pull Request email to Linus Torvalds for any
maintainer branch inside the `kdevkit` Parent Workspace (`linux/`), completely
**without StGit**, and stages the resulting email as a strict plain-text draft
in the local **UndineD** Maildir `Drafts` folder via the `undine` MCP server.

### Core Safety Invariants

1. **Zero SMTP Transmission**: Never send email directly or invoke `git send-email`. Always stage via UndineD MCP `create_mail_draft` so the human maintainer reviews and sends manually in the UndineD Web UI.
2. **Mandatory Tag Review Checkpoint**: Never run `git tag -s` until the user explicitly reviews and approves the drafted tag description and tag name.
3. **Never Auto-Push**: Never run `git push` without explicit user instruction. Instead, report whether the signed tag has been pushed to the public remote.
4. **Zero `linux/` Tree Pollution**: Keep all temporary files under `/tmp/` or `.kdev/`—never create files inside `linux/`.

---

## Dependencies & Inputs

- **Git & GPG**: Pure Git (`git -C linux ...`) and `gpg-agent` for `git tag -s`.
- **Optional Phase 4 Context**: `.kdev/pr-context.json` (generated by VSCode command `kdev: Prepare Pull Request Context` / `kdev: Run Pull Request Skill`).
- **Bundled Script**: [`scripts/make-linus-pull`](./scripts/make-linus-pull) — Parent-Workspace-aware PR cover letter, Cc list, shortlog, diffstat, and diff generator.
- **UndineD MCP Server (`undine`)**: Uses `create_mail_draft` (see `undine-mcp-review` skill for schema details).

## Workflow

### Step 1: Identify Target Branch, Base Ref, and Commits

1. **Check for `.kdev/pr-context.json` first**:
   If `.kdev/pr-context.json` exists and matches the requested branch (or no branch was specified), read `branch`, `subsystem`, `cadence`, `baseRef`, `baseSha`, `headSha`, `existingSignedTags`, and `remotePushStatus` from it.
2. **Otherwise resolve directly via pure Git (`git -C linux`)**:
   ```bash
   BRANCH="${TARGET_BRANCH:-$(git -C linux symbolic-ref --short HEAD)}"
   BASE_REF="$(git -C linux config --get "branch.${BRANCH}.kdev-base" || echo origin/master)"
   BASE_SHA="$(git -C linux merge-base "${BASE_REF}" "${BRANCH}")"
   git -C linux log --reverse --oneline "${BASE_SHA}..${BRANCH}"
   ```
3. Inspect each commit in `${BASE_SHA}..${BRANCH}`:
   ```bash
   git -C linux log --reverse --stat "${BASE_SHA}..${BRANCH}"
   git -C linux show <sha>
   ```
4. Check recent subsystem tags to match naming conventions (e.g., `probes-fixes-v6.15-rc6`, `probes-v6.16`, `bootconfig-fixes-v7.2-rc1`):
   ```bash
   git -C linux tag -l --sort=-creatordate | head -n 20
   ```

---

### Step 2: Draft Tag Description & User Review Checkpoint (Mandatory)

Draft the annotated tag message following kernel maintainer conventions:

- **Header**:
  - `fixes` cadence: `<Subsystem> fixes for <version>:` (e.g. `Probes fixes for v6.15-rc6:`)
  - `for-next` / merge-window cadence: `<Subsystem> updates for <version>:` (e.g. `Probes updates for v6.16:`)
- **Grouping & Summaries**:
  - Group bullet points by functionality or subsystem prefix (e.g. `- kprobes: ...`, `- fprobe: ...`, `- init/bootconfig: ...`).
  - Provide 2–3 concise lines per logical change explaining **what the problem/need was** and **what changed and why**.
- **Line Width**: Hard-wrap all prose lines to **75 columns or fewer**.

#### Reference Format Example
```text
Bootconfig fixes for v7.4-rc1:

- init/bootconfig: Pass init arguments in documented order
  Parse extra_init_args before command-line init arguments in
  start_kernel(). This ensures command-line options take precedence over
  bootconfig, matching the documented order and saved command line.
```

> [!IMPORTANT]
> **STOP HERE AND WAIT FOR USER APPROVAL.**
> Present the proposed:
> 1. Target branch & base commit (`${BRANCH}` on `${BASE_REF}`)
> 2. Proposed tag name (e.g. `<subsystem>-fixes-<version>`)
> 3. Proposed email subject (`[GIT PULL] <subsystem>: Fixes for <version>`)
> 4. Full drafted tag description
>
> Do **not** proceed to Step 3 until the user approves or edits the draft.

---

### Step 3: Create GPG-Signed Git Tag

Once the user approves (or if an approved signed tag already points to `HEAD` and the user chooses to reuse it):

1. Write the approved tag message to `/tmp/tag-msg-<tag-name>.txt`.
2. Create the GPG-signed tag on the target branch tip:
   ```bash
   git -C linux tag -s "<tag-name>" -F "/tmp/tag-msg-<tag-name>.txt" "${BRANCH}"
   ```
   > [!NOTE]
   > GPG signing requires access to the user's `gpg-agent` and `~/.gnupg`. If the execution environment sandboxes `~/.gnupg`, inform the user or run with user-approved host access.
3. Verify the tag object and clean up the temp file:
   ```bash
   git -C linux cat-file tag "<tag-name>"
   rm -f "/tmp/tag-msg-<tag-name>.txt"
   ```
4. Check whether the tag is already pushed to the public remote (read-only check; **do not push automatically**):
   ```bash
   git -C linux ls-remote origin "refs/tags/<tag-name>"
   ```

---

### Step 4: Generate Pull Request Text & Cc List (`scripts/make-linus-pull`)

Run the bundled [`scripts/make-linus-pull`](./scripts/make-linus-pull) script:

```bash
.agents/skills/kdev-pull-request/scripts/make-linus-pull \
  -C linux \
  --from "${BASE_SHA}" \
  --repo "${PUBLIC_REPO_URL}" \
  "<tag-name>"
```

- `--repo` defaults to `git config branch.<branch>.kdev-pull-repo`, then `git://git.kernel.org/pub/scm/linux/kernel/git/trace/linux-trace.git` (override via `--repo` for other trees).
- Output is written to `/tmp/prog-<tag-name>`:
  - **Line 1**: Comma-separated `Cc:` recipients (patch authors plus standard maintainers/lists).
  - **Line 2–3**: Blank lines.
  - **Line 4 onwards**: Complete pull request body addressed to Linus (tag description, pull URL, tag name, Tag SHA1, Head SHA1, shortlog, diffstat, and commit diff).

---

### Step 5: Stage Plain-Text Draft in UndineD via MCP (`create_mail_draft`)

1. Read `/tmp/prog-<tag-name>`:
   - Split **Line 1** by comma, trim whitespace, and deduplicate into a `cc: string[]` list.
   - Take **Line 4 onwards** verbatim (preserving raw `\t` tabs and newlines) as `body`.
2. Append the maintainer signature if not already present:
   ```text
   -- 
   Masami Hiramatsu (Google) <mhiramat@kernel.org>
   ```
   *(Or use `git -C linux config user.name` / `user.email` if different.)*
3. Call UndineD MCP tool `create_mail_draft` (`ServerName: "undine"`):
   - `to`: `["Linus Torvalds <torvalds@linux-foundation.org>"]`
   - `cc`: extracted `string[]` Cc list
   - `subject`: `"[GIT PULL] <subsystem>: Fixes for <version>"` (or `Updates for <version>`)
   - `body`: full pull request body with signature
   - `tags`: `["PR-Draft"]`
4. Report the returned `draft_id`, `message_id`, `maildir_path`, and `web_url` to the user, and remind them:
   - Push the signed tag (`git -C linux push <remote> <tag-name>`) if `ls-remote` showed it is not yet published.
   - Review and manually send the draft in the UndineD Web UI (`web_url`).

## Configuring `kdev.git.prSkillCommand` (Optional)

To trigger this workflow directly from VSCode's **`kdev: Run Pull Request Skill`** command on any maintainer branch, set `kdev.git.prSkillCommand` in `.vscode/settings.json` to invoke your agent CLI with `{branch}` and `{contextFile}` (`.kdev/pr-context.json`).

## Common Mistakes

1. **Using StGit (`stg`)**: `kdevkit` is StGit-free. Always use `git -C linux` and `.kdev/pr-context.json`.
2. **Skipping the Review Checkpoint**: Never run `git tag -s` before the user approves the drafted tag description.
3. **Line Width Exceeding 75 Columns**: Wrap tag message prose to <= 75 columns.
4. **Calling Deprecated `write_draft_message` for Standalone PRs**: Always use `create_mail_draft` so `to`/`cc` arrays, `PR-Draft` tags, and raw `\t` diff tabs are handled cleanly.
5. **Forgetting to Check Remote Push Status**: Remind the user if the signed tag has not yet been pushed to the public Git tree before they click Send in UndineD.
